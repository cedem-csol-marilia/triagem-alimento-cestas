00Visão geral

O sistema nasceu de uma necessidade simples: o CEDEM recebia pedidos de cesta básica por um Google Form e controlava tudo na mão. O objetivo foi transformar isso numa operação que importa os cadastros sozinha, identifica famílias repetidas, prioriza quem mais precisa e acompanha cada entrega.

A arquitetura tem duas pontas que terminam no mesmo banco:

  • Cadastro e triagem: Google Form → Planilha → Apps Script → banco (normaliza e deduplica) → fila priorizada.
  • Automação de entregas: e-mails da loja → dois fluxos no Make → funções do banco (RPCs) → baixa automática.

O front é Next.js na Vercel; o banco e a autenticação são do Supabase. Tudo abaixo é a ordem real em que foi montado.

01Pré-requisitos

Instalar uma vez por máquina.

Você vai precisar de Node.js (que traz o npm e o npx), Git e um editor como o VS Code. Além disso, contas em Supabase, Vercel, Google (Form/Planilha/Apps Script) e Make.

Confira se Node e Git já estão instalados:

node -v      # precisa ser v18+ ou v20+
npm -v
git --version
Se o Node não aparecer: baixe a versão LTS em nodejs.org — o instalador já inclui npm e npx. No Windows, instale também o Git for Windows (git-scm.com).

02Criar o projeto Next.js

Um comando cria o esqueleto inteiro do app com TypeScript e App Router:

npx create-next-app@latest triagem-alimento-cestas

Respostas usadas no assistente:

PerguntaResposta
TypeScript?Yes
ESLint?Yes
Tailwind CSS?No (o projeto usa CSS próprio — o Axé Design System)
src/ directory?No
App Router?Yes
import alias (@/*)?Yes

Depois, entre na pasta criada:

cd triagem-alimento-cestas

03Instalar as dependências do Supabase

O create-next-app já instalou o Next, o React, o TypeScript e o ESLint. A única instalação manual foi o Supabase:

npm install @supabase/supabase-js @supabase/ssr
  • @supabase/supabase-js — o cliente que conversa com o banco e a auth.
  • @supabase/ssr — helper para usar o Supabase em Server Components do Next (sessão no servidor).

Na prática, você cria dois clientes: um para o navegador (lib/supabase/client.ts) e um para o servidor (lib/supabase/server.ts).

04Variáveis de ambiente

Crie um arquivo .env.local na raiz do projeto com as chaves do seu projeto Supabase:

NEXT_PUBLIC_SUPABASE_URL=https://SEU_PROJETO.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=sua_anon_key_aqui

Essas duas chaves ficam em Supabase → Settings → API.

Segurança: nunca commite o .env.local (ele já entra no .gitignore). E nunca use a chave service_role no app ou na automação — ela é de admin. No front, só a anon key.

05Rodar localmente

Com tudo no lugar, suba o servidor de desenvolvimento:

npm run dev      # abre em http://localhost:3000

Outros comandos úteis no dia a dia:

npm run build    # build de produção — também acusa erros de TypeScript
npm run start    # roda o build localmente
npm run lint     # checagem do ESLint
Dica: rodar npm run build antes de cada push pega erros de tipo que o dev às vezes deixa passar.

06Montar o banco no Supabase

Aqui está o coração do projeto.

O Supabase foi montado pelo painel web — não por uma CLI local. Cada mudança no banco foi escrita em SQL e aplicada no SQL Editor. A pasta supabase/ do repositório guarda a versão de tudo: cada alteração virou um arquivo SQL numerado.

1Criar o projeto

Em supabase.com → New Project, escolha a região e defina a senha do Postgres. Depois, em Settings → API, copie a URL e a anon key para o .env.local e para a Vercel.

2Ligar a autenticação por e-mail

Em Authentication → Providers, deixe o e-mail ligado. Para os e-mails de convite e de redefinição de senha, configure o SMTP (no projeto usei o do Gmail).

3Aplicar as migrations no SQL Editor

Cada mudança no banco é um arquivo com nome no padrão de data/hora, aplicado em ordem:

# formato do nome do arquivo
AAAAMMDDHHMMSS_descricao_curta.sql
# ex.: 20260617121000_rpcs_automacao_entregas.sql

Cole o conteúdo no SQL Editor e rode, do mais antigo para o mais novo. Sempre que criar ou alterar uma função (RPC), rode também:

notify pgrst, 'reload schema';  # o PostgREST recarrega a API

4A estrutura da pasta

supabase/
├── ARQUITETURA.md          # mapa do fluxo de dados (ler primeiro)
├── migrations/             # histórico real: 1 arquivo por mudança
│   └── AAAAMMDDHHMMSS_*.sql
└── schema/                 # snapshot do estado atual
    ├── tables/
    ├── views/
    └── functions/

5O modelo de dados

As tabelas principais:

TabelaPapel
respostas_formsinput cru do Google Form (só o Apps Script escreve aqui)
familiascadastros consolidados — o registro "oficial" de cada família
duplicatas_detectadaspares de cadastros suspeitos de serem a mesma casa
ciclos / entregasciclos de 3 meses e as entregas individuais (núcleo da automação)
entregas_nao_casadasfila de exceções: o que a automação recebeu mas não casou
config_pesos_*pesos do score e da regra de duplicata (ajustáveis sem código)

E as funções de banco (RPCs) que fazem o trabalho pesado: importar_resposta_forms, detectar_duplicatas, calcular_score, mesclar_familias, e as da automação (registrar_pedido_loja, registrar_entrega_concluida, resolver_nao_casada).

Por que tudo passa por RPC? Uma RPC é uma função guardada dentro do banco que você chama de fora como se fosse um endpoint. Em vez de mandar um UPDATE cru, o app e o Make chamam uma RPC que normaliza, valida, evita duplicar e — na dúvida — joga numa fila de revisão. É o que garante que ninguém escreve no escuro.

07Ingestão do Google Form (Apps Script)

  1. Vincule as respostas do Form a uma Planilha.
  2. Na Planilha: Extensões → Apps Script.
  3. Cole o script (em docs/apps-script/ingestao-forms.gs). Ele lê por nome de coluna, então não quebra se você reordenar o formulário.
  4. Configure um gatilho (trigger) para rodar a cada nova resposta.

A cada resposta, o script faz um POST na RPC importar_resposta_forms do Supabase (usando a anon key), que normaliza os dados, procura duplicata e insere na fila — ou marca para triagem, se houver suspeita.

08Automação de entregas (Make)

São dois fluxos no Make, e os dois casam a família pelo WhatsApp:

  • Fluxo do pedido: lê o e-mail de pedido da loja → chama registrar_pedido_loja.
  • Fluxo da entrega: lê o e-mail de entrega/NF → chama registrar_entrega_concluida / registrar_nf.

Cada fluxo faz um POST numa RPC do Supabase (/rest/v1/rpc/<funcao>). As regras de ouro:

  • Só escreve via RPC — nunca UPDATE direto.
  • As RPCs são idempotentes: se o Make repetir a chamada, não duplica a entrega.
  • O que não casa cai em entregas_nao_casadas e é resolvido na tela /nao-casadas.
Nunca use a service_role no Make. Use chave restrita / RPC.

09Versionar e publicar (Git + Vercel)

Primeiro, suba o código para o GitHub:

git init
git add .
git commit -m "deploy inicial"
git branch -M main
git remote add origin https://github.com/SEU_USUARIO/triagem-alimento-cestas.git
git push -u origin main

Depois, na Vercel:

  1. New Project → importe o repositório do GitHub.
  2. Em Environment Variables, adicione NEXT_PUBLIC_SUPABASE_URL e NEXT_PUBLIC_SUPABASE_ANON_KEY.
  3. Deploy. A partir daí, todo push na main faz redeploy automático.

10Lições que valem o aprendizado

Algumas decisões pouparam muita dor:

  • Qualidade começa na origem. Endereço como texto livre quebra qualquer deduplicação. Separar CEP, número e complemento no Form destrava o resto.
  • Simples e validado vence esperto demais. A régua de "é a mesma casa?" foi calibrada à mão contra um gabarito real — uma regex "inteligente" só piorava.
  • Humano no comando. O sistema sugere; a pessoa decide quem é duplicata e a prioridade. Tema sensível não pode ser 100% automático.
  • Versione tudo. Cada mudança no banco é uma migration, e um arquivo "continuar aqui" recupera o contexto em qualquer retomada.
